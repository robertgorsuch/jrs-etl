# ORDERS_LOAD: works in Studio, dies on the Linux server

Three symptoms, but they are not three independent problems. One is an operations
mistake in how the launcher is called; the other two are latent design bugs in the
job that Studio never exercised because, in Studio, the job ran with a complete
context against DEV data. The wrong context on the server is very likely what
exposes the tMap NullPointerException, so fix it first and re-test before touching
the job - but both Java errors still need a code fix, because they are only waiting
for the right data to appear.

## 1. "Context values seem wrong on the server" - the launcher is running the Default context

### What is happening

Open `ORDERS_LOAD/ORDERS_LOAD_run.sh`. The last line generated by Studio looks like:

```sh
java ... orders.orders_load_0_1.ORDERS_LOAD --context=Default "$@"
```

`--context=Default` is the context that was selected in the Build Job dialog, baked
into the launcher; `"$@"` forwards whatever ops append. So this command:

```sh
./ORDERS_LOAD_run.sh --context_param DB_HOST=prod-db
```

means: *load the `Default` context group, then override exactly one variable,
`DB_HOST`*. Every other context variable - `DB_PORT`, `DB_NAME`, `DB_USER`,
`DB_PASS`, input/output directories, batch sizes, dates, flags - keeps the value of
the `Default` column, which in most projects is the developer's DEV values. In
Studio nobody noticed because the Run view's Context drop-down was set to the
right context group (all values present), not to `Default` + one override.

That is also why the job "connects" (it reaches `prod-db`) but then behaves
strangely: it is talking to the prod host with DEV database name / user / schema /
paths, or reading a lookup table or file that is empty or absent on the server.

### Fix

Pass the context group **and** the override. The generated `main()` parses
arguments in order and the last `--context` wins, so appending works:

```sh
./ORDERS_LOAD_run.sh --context=PROD --context_param DB_HOST=prod-db
```

Checks before relying on it:

1. **The PROD context must be in the build.** Studio only exports the contexts
   ticked under `Context scripts` in the Build Job dialog. Look in the zip for
   `ORDERS_LOAD/<project_lower>/orders_load_0_1/contexts/PROD.properties`
   (and `Default.properties`). If `PROD.properties` is missing, the job prints
   `Could not find the context PROD` and silently continues with defaults -
   exactly the symptom you have. Rebuild with all contexts ticked (and
   `Apply to children` if the job calls child jobs with tRunJob).
2. **Names are case-sensitive**, both the context group (`PROD` not `prod`) and the
   variable (`DB_HOST` not `db_host`). A misspelled variable is ignored with at most
   a warning.
3. **Unknown arguments are ignored silently.** `--context-param`,
   `--context_params`, `--contextParam` all do nothing. The pair after
   `--context_param` must be one shell token with no spaces around `=`:
   `--context_param "IN_DIR=/data/in dir"` is right, `--context_param IN_DIR = /x`
   is wrong.
4. **All CLI values arrive as strings** and are parsed to the declared type at
   start-up: `Integer`/`Long` parse strictly, `Date` expects
   `yyyy-MM-dd HH:mm:ss` by default, empty string becomes `null`. A bad value
   either fails at start or leaves the variable `null` (see problem 2).
5. **Check `jobInfo.properties`** at the zip root: `contextName=` tells you the
   baked-in default, `date=` tells you when it was built. If that date is before
   the last Studio change, ops are running a stale export, and no amount of
   debugging the current Studio job will match the server behaviour.
6. **Something inside the job may be overwriting the CLI values.** Precedence,
   highest first: an explicit `tContextLoad` component, then Implicit Context Load
   (Job view > Extra tab, or Project Settings > Job Settings), then
   `--context_param`, then the selected context group, then `Default`. If the job
   uses Implicit Context Load from a file, that file must exist *on the server* at
   the configured path; if it does not, the job falls back to the baked-in values
   with only a warning. Turn `Print operations` on so each assignment is logged.
7. **An extracted `contexts/*.properties` next to the launcher overrides the copy
   inside the jar** (the job folder is first on the classpath). If someone on the
   server "fixed" `Default.properties` by hand, those edits are live and
   invisible to Studio.

### How to see what the job actually ran with

Add a `tJava` at the start of the job (or in `tPrejob`) with:

```java
System.out.println("Running context: " + contextStr);
System.out.println(context.toString());   // dumps every key=value; mask passwords before leaving this in
```

`contextStr` is the name of the context group the job resolved. Also run the
launcher with `--watch` so the end-of-run line shows the exit code. For a quick
offline look at what ops were given, the skill ships an inspector that prints the
launcher's hard-coded `--context`, the bundled context files, `jobInfo.properties`,
drivers in `lib/` and the exact run command:

```sh
python3 scripts/inspect_job_export.py ORDERS_LOAD_0.1.zip
```

Longer term: make `Default` safe (point it at DEV, never PROD), hand ops a wrapper
or cron line that always passes `--context=PROD`, keep secrets out of
`--context_param` (they show in `ps -ef` and scheduler logs - use a `Password`
typed variable with an `enc:` value, Implicit Context Load from a root-only file,
or TAC/TMC task parameters), and pin `-Duser.timezone=UTC` and
`-Dfile.encoding=UTF-8` in the Studio JVM arguments before building so cron's
`POSIX` locale does not change date and encoding behaviour.

## 2. `Exception in component tMap_2 (ORDERS_LOAD) java.lang.NullPointerException`

### What is happening

tMap expressions are compiled into Java. An NPE in tMap means one of:

- **Unboxing `null` into a primitive.** In the schema editor, an `Integer`, `Long`,
  `Double`, `Boolean`, `Short`, `Float`, `Byte` or `Character` column with
  `Nullable` unchecked generates a primitive (`int`, not `Integer`). When a `null`
  arrives from the source, from an expression like `cond ? 0 : null`, or from a
  lookup, Java calls `.intValue()` on `null` and throws. The generated-code line in
  the trace usually ends in `.intValue()` / `.doubleValue()` / `.booleanValue()`.
- **Lookup miss on a Left Outer Join.** tMap_2 has one or more lookup flows (the
  dashed `row` links). With `Join Model = Left Outer Join` a main row with no match
  still goes out, and every column of that lookup is `null`. Any expression that
  reads `lkp.col` unguarded, or maps it into a non-nullable output column, blows up.
- **Method call on a null String** - `row1.customer_code.trim()`,
  `row1.status.equals("X")`, `row1.region.toUpperCase()`, `TalendDate.parseDate(..., row1.d)`.
- **A null context variable** used in an expression: `context.BATCH_SIZE.intValue()`,
  `context.DEFAULT_CURRENCY.trim()`. This is the direct link to problem 1: a
  variable that is empty in the `Default` column, or whose value failed type
  parsing, is `null` on the server while it was filled in the context group you
  chose in Studio.

Why it never happened in Studio: DEV data had no nulls in those columns and every
lookup key matched its DEV reference table. On the server the job reads PROD
orders (reached through `DB_HOST=prod-db`) while its lookup still points at the DEV
database/schema/file named in `Default` - so either real PROD nulls or
wholesale lookup misses reach tMap_2 for the first time. Note also that `Die on
error` on the input components does not cover this: an NPE in tMap is an uncaught
Java exception, so the job dies with exit code 1 regardless.

### Find the exact expression

The stack frame `at <project>.orders_load_0_1.ORDERS_LOAD.tXxx_1Process(ORDERS_LOAD.java:NNNN)`
names the *subjob* (its start component), not the failing component; the failing
component is the `Exception in component tMap_2` line above it. Open the job in
Studio, `Code` view, `Ctrl+L` to line `NNNN`; the generated comment block above it
names the output table / column / Var being evaluated. Make sure the Studio job is
the same version as the export (compare `jobInfo.properties`), or rebuild with
`Source files` ticked so the `.java` ships inside the zip.

### Fix

1. Re-run with the correct context (problem 1). If the NPE disappears, the trigger
   was a lookup miss or null context variable caused by DEV values - but still do
   steps 2-4, because PROD data will eventually contain the same nulls.
2. In tMap_2's schema editor, tick `Nullable` on **every lookup column you read**,
   every optional source column, and the corresponding output columns. Rule of
   thumb from the reference: "every lookup column you read and every optional
   source column is Nullable".
3. Guard expressions:
   ```java
   row2.unit_price == null ? 0d : row2.unit_price
   row1.customer_code == null ? null : row1.customer_code.trim()
   Relational.ISNULL(row1.status) ? "UNKNOWN" : row1.status
   row2.id != null ? row2.region : "N/A"          // test the lookup key, not a payload column
   row1.qty != null && row1.qty > 0               // in output filters, test null first
   ```
   Keep ternary branches type-compatible (`cond ? null : 1` is `Integer`;
   `cond ? 0 : null` compiles but NPEs when the target is `int`).
4. Decide what a lookup miss means. If the row is invalid without the lookup, set
   `Join Model = Inner Join` and add an output with `Catch lookup inner join
   reject` to log/park those rows instead of crashing. If it is acceptable, keep
   Left Outer Join and default the columns as above. Add a `tLogCatcher` so the
   failing row context lands in a log table rather than only on stdout.
5. If the NPE is on a `context.X` expression, give `X` a value in **every** context
   column (including `Default`) and make sure the value parses to the declared type.

## 3. `java.lang.ClassCastException: java.lang.Long cannot be cast to java.lang.Integer` in tJava_1

### What is happening

`globalMap` is `Map<String, Object>`, so every read is a cast you wrote by hand:

```java
int n = ((Integer) globalMap.get("tDBOutput_1_NB_LINE_INSERTED"));
```

The stored object is a `java.lang.Long`, the cast says `Integer`, and Java throws
at run time (the compiler cannot check it). Typical sources of a `Long` where you
expected `Integer`:

- A global that is actually typed `Long` by its component. Most `NB_LINE`-style
  counters are `Integer`, but not all; types differ per component and per release,
  and the Outline view (Window > Show view > Talend > Outline, hover the variable)
  is the only reliable source. Examples of `Long`s: `tDBLastInsertId`'s
  `last_insert_id`, tStatCatcher durations, anything you stored yourself from a
  `Long` typed column.
- A `tSetGlobalVar` or `tFlowToIterate` value fed by a column typed `Long`
  (`BIGINT`, `COUNT(*)` on MySQL/PostgreSQL, a `tAggregateRow` `sum`/`count`
  output you changed to `Long`), while tJava_1 still casts to `Integer`.
- The same key written in two places with different types (for example a
  `tSetGlobalVar` in one branch and a `tJavaRow` in another), so what tJava_1 sees
  depends on which branch ran.

Why "sometimes", and why not in Studio: the cast only runs when tJava_1 runs and
only against whatever last wrote that key. On the server a different branch
(`Run if`, `OnComponentOk` vs `OnSubjobError`, a non-zero count that was always 0
in DEV) is taken, or a different child-job version is bundled (tRunJob `Latest`),
or the deployed export predates/postdates a schema change in Studio. It is a
latent bug that DEV never reached.

### Fix

1. In tJava_1, replace every typed cast on a numeric global with a type-agnostic
   one plus a null guard:
   ```java
   Object o = globalMap.get("tDBOutput_1_NB_LINE_INSERTED");
   long inserted = (o == null) ? 0L : ((Number) o).longValue();
   // or, when text is all you need:
   String s = String.valueOf(globalMap.get("tDBOutput_1_NB_LINE_INSERTED"));
   ```
   `((Number) o).intValue()` works when the consumer must be an `int`, but prefer
   `long` for row counts (the reference recommends `Long` for counts and ids
   above 2^31).
2. Check every global tJava_1 reads in the Outline view and align the cast; if you
   drag the variable from the Outline into the editor, Studio inserts the correct
   cast form for you.
3. If the key is one you set yourself (`globalMap.put(...)`, `tSetGlobalVar`),
   make all writers use the same type.
4. Rebuild, redeploy the new zip, and confirm with `jobInfo.properties` `date=`
   that the server is running the build you just made.
